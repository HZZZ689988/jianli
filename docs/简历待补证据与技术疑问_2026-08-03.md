# 简历待补证据与技术疑问

更新时间：2026-08-03<br>
用途：这份文档只用于向指导工程师、项目负责人或自己的工作记录补证，不建议随简历公开。涉及公司源码、固件、内网地址和完整日志时，只保留脱敏后的参数、时间和结论。

## 一、记录原则

简历可以先保留本人确认做过的功能，但下面这些细节不能直接套用“行业常见值”。最终应以链接脚本、设备树、协议头文件、串口/CAN日志、测试记录或产线报告为准。

- “双分区”至少要能说清 Flash 布局、活动分区、待确认分区和回滚条件。
- “CRC32”至少要确认计算范围、字节序和参数；只说 CRC32 仍可能与对端不兼容。
- “ACK/重传”至少要确认 ACK 粒度、超时时间、最大重试次数和重复帧处理。
- CAN 的 500 kbit/s 是总线标称位速率，不是固件有效传输速率。
- 产线“通过考核”需要有考核对象、测试项目、成功判据和结果记录。

## 二、手持终端电源与深睡眠

### 需要确认的问题

1. “深睡眠”具体指谁进入低功耗：RK3562 的 suspend/休眠，还是 STM32F103 的 Sleep、STOP 或 Standby？
2. 进入深睡眠的触发条件是什么：开机短按、电源状态机命令、UART命令，还是 RK 侧服务主动执行？
3. 唤醒源是什么：电源键 GPIO、MCU 到 RK 的中断脉冲、RTC、充电插入还是其他信号？
4. 深睡眠前后哪些电源轨和外设仍保持工作？屏幕、图传、Wi-Fi、MCU、充电检测分别是什么状态？
5. 是否有以下任一种证据：
   - RK 侧 suspend/resume 日志；
   - STM32 `PWR->CR/CSR` 或 STOP/Standby 相关代码；
   - 示波器上的按键、PWRON、电源轨和唤醒时序；
   - 深睡眠前后的整机电流数据。

### “预留安全关机时间”需要确认

1. MCU 通过哪个信号触发 RK3562 关机：`PWRON`、UART命令、GPIO中断还是组合方式？
2. PWRON 的有效电平和保持时间是多少？
3. MCU 在切断 `Vsys_CTRL`、`P5V_PHE_CTRL` 前等待多久？是固定延时，还是等待 RK ACK、状态脚、心跳消失或 power-good 变化？
4. 等待超时后是继续供电、强制断电，还是记录异常后重试？
5. 是否有一次完整日志或示波器截图，能对应“用户长按 → RK开始关机 → 文件系统/服务退出 → MCU切断受控电源”？

建议形成一张脱敏时序图，至少标出按键、MCU状态、PWRON、RK应答、外设电源和系统电源。

## 三、手持终端 UART 双分区升级

### Flash布局必须重新确认

芯片为 STM32F103RCT6、内部 Flash 256 KB。该容量档通常按 2 KB Flash 页擦除，因此所有 Bootloader、metadata、Slot A、Slot B 边界都应按 2 KB 对齐。

此前口述的“每个分区约117 KB”不是 2 KB 的整数倍，不能直接作为最终地址写进简历。请从链接脚本、map文件或升级代码中确认：

1. Bootloader 起止地址和实际占用大小。
2. metadata/设备参数是否独立占页，是否有双备份。
3. Slot A、Slot B 的准确起止地址和最大镜像长度。
4. 两个 APP 是分别链接到不同地址，还是通过统一链接地址加拷贝/映射方式启动？
5. 中断向量表和 `SCB->VTOR` 如何根据活动分区设置？

一个满足 2 KB 页对齐的候选布局是“24 KB Bootloader/metadata + 116 KB Slot A + 116 KB Slot B”，但这只是用于核对的候选方案，不能在没有源码或map文件的情况下当成项目事实。

### UART升级协议需要确认

1. 波特率和串口格式是否仍为 115200 8N1？
2. 升级协议是否与 CAN 驱动板采用相同状态机：握手/开始、镜像信息、数据、结束、校验、切换？
3. 每个UART数据帧的帧头、命令、序号、长度、payload和校验字段分别占多少字节？
4. 是每帧CRC、分块CRC，还是只做整包CRC32？运行时协议的CRC16与升级协议不要混写。
5. ACK是逐帧、逐块还是滑动窗口确认？超时多久、最多重试几次？
6. ACK丢失时，MCU如何识别重复数据，避免重复写Flash或重复推进偏移？
7. 约1分钟升级时间从哪里开始计时、到哪里结束？固件实际大小、传输时间、Flash擦除时间、重启和确认时间分别是多少？
8. 120秒是等待RK启动并开始传输的窗口，还是整个升级总超时？超时后如何选择旧分区？

### A/B回滚需要确认

1. metadata是否包含 `active/pending/confirmed/invalid` 或等价状态？
2. 新镜像整包CRC32通过后，是先标记 pending 再重启，还是直接修改活动分区？
3. APP在什么条件下写“确认成功”：进入main、调度器启动、与RK通信成功，还是完成业务自检？
4. 启动失败计数保存在内部Flash、备份寄存器还是其他非易失区？允许失败几次？
5. metadata写入时断电如何处理？是否有双副本、递增序号和metadata CRC？
6. 升级中断电、校验失败、新APP看门狗复位和确认写入时断电分别会启动哪个分区？

## 四、驱动板 CAN 双分区升级

### 已确认的基础事实

- MCU：STM32F103CBT6，128 KB Flash。
- 两个 APP 分区：每个 52 KB，而不是 53 KB。
- 总线标称位速率：500 kbit/s。
- 整包校验：CRC32。
- 单轮升级约20秒，做过数十轮真机验证。

### Flash布局约束

STM32F103CBT6 这一容量档按 1 KB Flash 页擦除。52 KB 正好对应 52 个擦除页，分区边界应按 1 KB 对齐。

一个便于核对的候选布局是：

```text
0x08000000 - 0x08005FFF   Bootloader / metadata / 参数区，共24 KB
0x08006000 - 0x08012FFF   Slot A，52 KB
0x08013000 - 0x0801FFFF   Slot B，52 KB
```

该布局在算术和页对齐上成立，但仍需用真实链接脚本或map文件确认。剩余24 KB是否全部属于Bootloader，还是还包含metadata、校准参数、版本信息，也需要拆开说明。

### CAN协议应受以下通用约束

经典 CAN（ISO 11898-1 / CAN 2.0）单帧数据区最多8字节，因此简历不应只写“把固件分包后发送”，还应确认：

1. 使用标准帧还是扩展帧，CAN ID如何区分升级命令和设备节点？
2. 升级是否分为 START、DATA、END/VERIFY、STATUS/ACK 等命令状态？
3. DATA帧中序号、命令/标志和固件数据各占多少字节，单帧真实固件载荷是多少？
4. ACK是逐帧、每N帧还是每个Flash块确认？是否有流控，避免MCU擦写Flash时CAN接收队列溢出？
5. ACK超时和最大重试次数是多少？重复序号是再次写入、忽略后ACK，还是报错？
6. CAN控制器硬件ACK只能说明总线上有节点正确接收，应用层ACK如何证明Bootloader已经解析并接受该数据？
7. 整包CRC32计算的是bin有效长度还是完整52 KB槽位，尾部 `0xFF` 是否参与？
8. CRC32 的多项式、初值、输入/输出反射和最终异或值是什么？不要只根据“使用了 STM32 硬件 CRC”推断参数：STM32F1 CRC 外设默认多项式虽为 `0x04C11DB7`，其数据输入方式和最终结果未必等同于常见的软件 CRC-32/ISO-HDLC。建议让 RK 与 MCU 对同一段测试数据输出中间值和最终值，再确认双方完全一致。
9. 20 秒总时长中，Flash 擦除、数据发送、ACK 等待、重传、整包校验和重启各占多少？估算时应使用 `ceil(镜像字节数 / 单帧真实固件载荷)` 计算数据帧数量，再叠加 CAN 帧开销、应用层 ACK、Flash 写入等待和重启时间，不能直接用 52 KB 除以 500 kbit/s。

在这些字段未确认前，公开简历只写“按经典CAN 8字节载荷约束设计开始/数据/结束状态、序号、ACK/超时重传和整包CRC32”，不写未经证实的单帧载荷或ACK窗口大小。
